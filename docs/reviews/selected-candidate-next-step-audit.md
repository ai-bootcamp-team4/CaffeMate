# 후보 선택 이후 다음 단계 독립 감사

## 결론

현재 화면은 **준비 화면이 아니라 선택 결과와 준비 목록을 읽기만 하는 화면**이다. 후보 선택은 실제로 저장되지만, 사용자가 점포 자료를 입력하거나 문서를 올리거나 재계산을 시작할 수 있는 동작이 연결되어 있지 않다. 그래서 화면의 문구는 “자료를 추가하면 다시 계산한다”고 약속하지만 사용자는 그 일을 시작할 수 없다.

PoC에서 가장 먼저 연결할 한 가지는 **실제 점포 조건 입력**이다.

```text
후보 선택
→ 실제 점포 조건 입력
→ 보증금·월세·관리비·권리금·면적을 후보에 반영
→ 초기 필요자금과 월 고정비 재계산
→ 이전 임시값과 달라진 결과 표시
```

공식 창업 절차는 이 흐름을 보조하는 안내다. 현재처럼 자료 입력보다 앞에 두거나 여섯 개의 빈 상태를 크게 보여주면 안 된다.

## 1. 이 화면에서 사용자가 정확히 해야 하는 일

제품 정본의 후보 선택 이후 흐름은 `후보 선택 → 실제 자료 추가 → 충돌 확인과 재계산 → 계약 전 판단 자료`다. 정본은 실제 매물과 임대 조건, 견적, 대출 조건, 프랜차이즈 문서를 추가 대상으로 명시한다. 따라서 사용자가 이 화면에서 해야 할 일은 체크리스트를 읽는 것이 아니라 다음 셋 중 하나를 실행하는 것이다.

1. 가장 먼저 검토할 실제 점포 하나의 조건을 직접 입력한다.
2. 매물 자료나 견적 파일이 있으면 올린다.
3. 입력한 실제 값으로 다시 계산된 결과에서 계속 검토할지, 조건을 바꿀지 판단한다.

첫 동작은 자료가 가장 적게 필요한 **점포 조건 직접 입력**이어야 한다. 필수 입력은 주소 또는 매물 이름, 보증금, 월세, 관리비, 권리금, 면적이다. 층과 시설 상태는 선택 입력으로 두어도 된다. 사용자가 아직 점포를 찾지 못했다면 `점포를 아직 못 찾았어요`를 눌러 점포 탐색에 필요한 조건만 받거나 결과 비교로 돌아갈 수 있어야 한다.

## 2. 현재 경험이 행동으로 이어지지 않는 이유

### A. 가장 중요한 동작이 없다

화면은 `property_intake_enabled`와 `document_intake_enabled` 값을 근거로 “입력할 수 있다”고 설명한다. 그러나 실제 구성 요소에는 입력 폼, 파일 선택, 자료 추가 버튼, 재계산 버튼이 없다. 현재 버튼은 `결과 비교로 돌아가기` 하나뿐이다.

프론트 API도 후보 선택과 준비 안내 조회까지만 제공한다. 백엔드에는 문서 업로드와 추출 폼 API가 있지만 프론트 API 계약과 화면에서 호출하지 않는다. 점포 조건을 직접 입력하는 공개 API는 확인되지 않았다.

### B. 준비 목록의 모든 항목이 같은 중요도로 보인다

선택 응답은 모든 개인카페 후보에 매물, 임대 조건, 면적, 인테리어, 장비, 자금, 공급 조건을 한꺼번에 `REQUIRED`로 붙인다. 사용자는 무엇부터 해야 결과가 가장 크게 달라지는지 알 수 없다. 이유 문구도 여섯 항목에 동일하게 “개념 후보를 실제 점포 조건으로 검증해야 합니다”라고 반복된다.

PoC에서는 다음 우선순위로 줄이는 편이 낫다.

1. 점포와 임대 조건: 주소, 면적, 보증금, 월세, 관리비, 권리금
2. 큰 일회성 비용: 인테리어와 장비 견적
3. 자금 조달과 공급 조건

첫 묶음만 입력해도 임시 계산값을 실제 값으로 바꾸는 제품 가치를 보여줄 수 있다.

### C. 공식 절차가 핵심 동작처럼 보이지만 운영 데이터가 없다

준비 안내 서비스는 여섯 절차를 `get_official_procedure`로 동시에 조회한다. 하지만 현재 프로덕션 MCP 능력 목록에는 이 도구가 없다. 내부 데이터 조사 문서도 공식 절차 도구와 corpus가 아직 운영에 연결되지 않았다고 기록한다. 따라서 여섯 개의 “공식 자료를 불러오지 못함”은 일시적인 사용자 오류가 아니라 현재 배포 능력의 예상 결과다.

공식 절차는 계약 전 의사결정의 비용과 위험을 갱신하는 주 입력이 아니다. PoC에서는 화면 아래의 접힌 `나중에 확인할 공식 절차`로 내리고, 실제 원문이 연결된 항목만 보여주는 편이 정확하다.

### D. 선택 완료와 준비 완료의 경계는 설명하지만 진척 상태는 없다

현재 화면은 “검토 대상으로 선택했다”고 올바르게 설명한다. 그러나 선택 뒤 생성된 작업, 완료한 자료, 다음으로 처리할 항목, 재계산 가능 여부를 저장하거나 표시하지 않는다. 체크리스트는 상태가 모두 고정된 요구 목록이며 사용자가 완료 처리할 수도 없다.

## 3. PoC에서 가장 작은 실제 다음 단계

### 추천: `실제 점포 조건 입력하기` 한 경로만 끝까지 연결

첫 화면의 중심 동작을 다음처럼 만든다.

```text
제목: 이 창업안을 실제 점포로 확인해 볼까요?
설명: 매물의 임대 조건을 넣으면 임시 비용을 실제 값으로 다시 계산해요.

[실제 점포 조건 입력하기]
[매물 자료 파일 올리기]  ← 파일 경로가 실제 동작할 때만 표시
[아직 점포를 못 찾았어요]
```

직접 입력 폼:

| 항목 | 필요 여부 | 결과 영향 |
| --- | --- | --- |
| 주소 또는 매물 이름 | 필수 | 선택 후보와 점포 연결 |
| 면적 | 필수 | 운영 모델과 시설 비용 검토 |
| 보증금 | 필수 | 초기 필요자금 재계산 |
| 월세 | 필수 | 월 고정비 재계산 |
| 관리비 | 선택 | 월 고정비 재계산 |
| 권리금 | 선택, 모르면 미정 | 초기 필요자금과 누락 상태 갱신 |
| 층과 시설 상태 | 선택 | 위험과 추가 확인 항목 갱신 |

제출 뒤에는 다음 세 값만 먼저 보여도 PoC가 성립한다.

- 초기 필요자금: 이전 참고 범위와 실제 입력 반영값 비교
- 월 고정비: 이전 참고 범위와 실제 입력 반영값 비교
- 판단 변화: 예산 범위 안인지, 추가 확인이 필요한지

이 경로는 사용자가 입력한 사실을 권위 State에 반영하고 결정론적으로 재계산해야 한다. 모델은 입력값을 만들거나 계산하지 않는다.

| 공식 절차 데이터 | 준비 안내 서비스와 MCP 도구 계약 | `get_official_procedure` 프로덕션 등록, 공식 corpus, 실제 원문 조회 검증 | 현재 빈 화면의 직접 원인 |
| 진행 상태 | 선택 Event와 선택된 후보 State | 자료별 완료 상태, 마지막 반영 시각, 다음 작업, 재계산 중·완료 상태 | 이후 개선 항목 |

## 5. 구현 우선순위

### P0 — 지금 연결

1. 준비 화면에 `실제 점포 조건 입력하기`를 주 동작으로 추가한다.
2. 점포 조건을 선택된 후보에 저장하는 공개 명령을 추가한다.
3. 저장 직후 비용·현실성 재계산을 시작하고 새 결과로 이동한다.
4. 이전 참고값과 실제 입력 반영값의 차이를 표시한다.

### P1 — 다음 연결

1. `매물 자료 파일 올리기`에서 기존 문서 업로드 API를 호출한다.
2. 업로드, 검사, 파싱, 자동 입력 폼, 사용자 수정, `반영하고 다시 계산`을 끝까지 연결한다.
3. 인테리어·장비 견적에도 같은 흐름을 재사용한다.

### P2 — 안내 보강

1. 공식 절차 corpus와 `get_official_procedure`를 운영에 연결한다.
2. 절차를 지역과 영업 형태에 맞춰 정렬하고 공식 원문 링크를 제공한다.
3. 절차는 준비 자료 입력을 방해하지 않는 보조 영역에 둔다.

## 6. PoC 수용 기준

- 후보 선택 뒤 1번의 주 동작이 명확하게 보인다.
- 사용자가 점포 조건을 직접 입력하고 저장할 수 있다.
- 보증금과 월세를 바꾸면 초기 필요자금 또는 월 고정비가 실제로 달라진다.
- 새 결과는 참고 가정과 사용자 입력 사실을 구분한다.
- 점포 자료가 없어도 `아직 점포를 못 찾았어요`로 막히지 않고 돌아갈 수 있다.
- 연결되지 않은 공식 절차 여섯 개를 핵심 결과처럼 반복 표시하지 않는다.
- “입력 가능” 문구는 실제로 눌러 실행할 경로가 있을 때만 표시한다.
