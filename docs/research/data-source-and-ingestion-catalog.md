# CaffeMate 실제 데이터 출처 및 수집 설계

## 1. 결론

초기 조사 당시 결과 카드가 비어 있던 주된 원인은 파싱 실패보다 **운영 데이터 연결 부재**였다. 이후 코드 기준 production capability에는 지역 해석, 상권 profile·관측, 지역 임대 benchmark, 프랜차이즈 후보군, 공정위 신고연도 창업금액, 공식 문서·절차와 source health connector가 단계적으로 추가됐다. 이 문서의 각 행은 현재 코드 구현 상태와 아직 배포·자료 승인이 필요한 경계를 별도로 표시한다.

세 선택지에 대한 판정은 다음과 같다.

1. **프랜차이즈는 모집 근거와 공정위 비용 근거를 분리한다.** `list_franchise_universe`의 회사 공식 가맹 안내가 개인 가맹 후보 자격을 결정하며, `get_franchise_disclosure`는 그 후보에 대해서만 공정위 브랜드 identity와 신고연도별 창업금액을 구조화 재무 근거로 보강한다. 공정위의 법적 정보공개서 등록번호·등록일·원문 버전과 특정 지역 출점 승인은 아직 같은 경로에서 닫히지 않으므로 각각 문서 확인과 본사 외부 확인으로 남긴다.
2. **코드 로직 결함도 있음: 공식 RAG가 빈 근거로 끝나는 직접 원인이다.** [RAG MCP envelope](../../mcp/src/rag-connectors.ts)는 검색 hit를 `data`에 넣으면서 `evidence_records=[]`로 반환한다. 이후 [EVIDENCE_ASSESS projection](../../api/app/agents/task_factory.py)은 모델 입력에서 `data=[]`로 줄이고 `evidence_records`만 유지한다. 따라서 RAG 검색이 성공해도 hit가 EvidenceRecord 후보로 변환되지 않아 Agent가 평가할 근거가 0건이 된다. 커넥터 부재가 전체 빈 결과의 주원인이고, 이 변환 누락은 현재 존재하는 공식 문서 경로까지 무력화하는 별도 결함이다.
3. **조사는 했지만 파싱을 못함: 현재 관측된 형태는 아님.** 현재는 검색 hit를 구조화 EvidenceRecord로 만드는 변환 자체가 없으므로 파서 품질을 평가할 단계까지 도달하지 않았다. 상권 수치 데이터는 RAG 파싱 대상이 아니며 API, 파일, SQL, 공간 질의로 들어와야 한다.

이 문서는 `accessed_at=2026-08-23`을 공통 접근일로 사용한다. 원문이 데이터 기준일이나 게시일을 명시하지 않으면 추정하지 않고 `BLOCKED_BY_DATA`로 표시한다. “실시간”은 API가 즉시 응답한다는 뜻일 수 있으므로, 반드시 관측값의 실제 기준일과 분리한다.

## 4. 실제 ingestion 설계

### 4.1 데이터 흐름

```text
공식 API·공개 파일·사용자 업로드
  -> immutable raw object
  -> source manifest와 checksum
  -> source-specific parser
  -> normalized tables
  -> identity resolution과 공간 join
  -> quality gate와 freshness gate
  -> Claim 후보
  -> EvidenceRecord v2
  -> support counter와 deterministic planner
  -> evidence freeze
  -> 근거가 있는 설명 또는 ABSTAIN
```

원본은 수정 불가능한 객체로 저장하고 `source_id`, 요청 매개변수, 응답 상태, `retrieved_at`, 원문이 밝힌 `published_at` 또는 `data_date`, 라이선스 스냅숏 해시, 콘텐츠 해시를 함께 남긴다. 원본 JSON·XML·CSV·PDF는 파서가 바뀌어도 재처리할 수 있어야 한다.

### 4.3 식별자와 join 규칙

- 법정동 코드는 토지·주소·실거래의 기준 키로 사용한다. 행정동 코드는 주민·행정 통계에 사용하며 법정동과 일대일이라고 가정하지 않는다.
- SGIS `adm_cd`와 경계 기준연도는 쌍으로 저장한다. 현재 코드에 과거 통계를 무리하게 붙이지 않고, 유효기간을 통한 시점 join을 사용한다.
- 서울 상권 코드는 서울 전용 네임스페이스로 둔다. 2024년 개편 전후 코드를 별도 버전으로 관리하고 전국 행정동 id로 치환하지 않는다.
- 건물은 도로명주소의 건물관리번호를 우선 사용하고, 토지는 PNU 또는 법정동 코드와 지번 조합을 사용한다. 일부 가림 지번은 개별 건물 Claim으로 승격하지 않는다.
- LOCALDATA는 인허가관리번호를 사건 키로 사용한다. 소진공 점포 id는 2025년 분류 개편 전후에 끊긴 것으로 처리한다.
- 사업자등록번호는 사용자가 적법하게 제공한 검증 건에만 사용하며 검색·추정하지 않는다. 로그와 분석 테이블에는 해시 또는 별도 비밀 저장소 참조만 남긴다.
- 프랜차이즈는 공정위의 가맹본부 id, 영업표지 id, 정보공개서 등록번호와 버전을 복합 키로 쓴다. 문자열 브랜드명 join만으로 합치지 않는다.

### 4.4 날짜, 중복, 출처 이력 규칙

1. `retrieved_at`은 CaffeMate가 받은 시각, `source_observed_at`은 API가 관측한 시각, `published_or_data_date`는 통계나 문서가 나타내는 기준일이다. 셋을 대체하지 않는다.
2. 분기 자료는 분기 말일을 임의 관측일로 꾸미지 않고 `period_start`와 `period_end`를 보존한다.
3. 같은 원천의 동일 자연키와 기준일이 겹치면 원문 수정시각과 콘텐츠 해시로 버전을 만든다. 수정본은 이전 원본을 삭제하지 않는다.
4. 서로 다른 원천의 비슷한 점포는 자동 병합하지 않는다. 정규화된 주소, 좌표 거리, 상호, 전화번호 해시, 인허가 id의 증거 점수로 후보 링크를 만들고 낮은 점수는 별개로 유지한다.
5. 상충값은 평균내지 않는다. `conflict_status=CONFLICT`로 만들고 각 원문을 함께 보존한다.

### 4.5 EvidenceRecord 승격과 실패 규칙

정규화된 한 행이 곧 EvidenceRecord는 아니다. Claim의 지리 범위, 기준일, 단위, 방법론, 원문 위치가 모두 채워지고 품질검사를 통과한 값만 `EVIDENCED_FACT`가 된다. 사용자 문서에서 사용자가 확인한 값은 `USER_CONFIRMED_FACT`, 계산 결과는 입력 근거 id를 가진 `DERIVED_RESULT`, 모델링 시나리오는 `DECLARED_ASSUMPTION`이다.

값을 얻지 못했거나 지역·시점·단위가 맞지 않으면 다음 형태로 `ABSTAIN`한다.

- `value_kind=UNKNOWN`
- typed `value=null`
- `freshness_status=UNKNOWN`
- `missing_context`에 필요한 데이터원, 지역, 기간, 승인 상태를 기록
- `durable_evidence_refs=[]`
- 화면에는 “확인되지 않음”과 다음 확인 행동을 표시

파서 오류, 인증 실패, 쿼터 초과, 빈 응답, 경계 join 실패, 데이터 기준일 초과는 모두 “0”이 아니다. 커넥터 health와 Claim 결과를 별도로 기록하고 이전 값을 자동으로 최신값처럼 재사용하지 않는다.

### 4.6 저장소 우선, 실시간 조회 예외 원칙

CaffeMate의 기본 경로는 요청 때마다 웹을 검색하는 방식이 아니라 **서버가 수집·검증한 자료를 먼저 조회하는 방식**이다. 자료 형태에 따라 저장과 검색 책임을 다음처럼 분리한다.

```text
공식 API·공개 파일
  -> Cloud Storage 원본과 manifest
  -> BigQuery 정규화·시점별 snapshot
  -> 결정적 SQL·공간 계산
  -> 구조화 MCP connector

공식 법령·절차·정보공개서 원문
  -> Cloud Storage 버전 원본
  -> Vertex AI RAG Engine corpus
  -> 관할·시행일·문서 버전 metadata filter
  -> 인용 가능한 RAG retrieval

사용자 업로드 문서
  -> 프로젝트별 격리 저장·가림·OCR
  -> 프로젝트 전용 corpus와 정형 fact
  -> 사용자 수정·확인 후 EvidenceRecord
```

[BigQuery scheduled query](https://docs.cloud.google.com/bigquery/docs/scheduling-queries)는 반복 SQL을 예약 실행할 수 있고, [Dataform](https://cloud.google.com/dataform)은 BigQuery 변환·품질검사·의존성을 코드로 관리할 수 있다. 원본은 [Cloud Storage soft delete와 객체 버전 관리](https://docs.cloud.google.com/storage/docs/object-versioning)를 보존 정책과 함께 사용한다. 문서는 [Vertex AI RAG Engine](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/rag-quickstart)으로 가져오고, 시행연도·관할·문서 버전 같은 파일 메타데이터로 검색 범위를 제한한다.

| 요청 종류 | 기본 경로 | 실시간 조회 허용 조건 | 결과 계약 |
|---|---|---|---|
| 인구, 카페 수, 개·폐업, 공개 프랜차이즈 수치 | BigQuery 최신 승인 snapshot | 적재 SLA를 넘었고 원 API로 최신 여부를 확인할 수 있을 때 | 실시간 값도 원본 저장·품질검사 전에는 임시 Evidence로만 취급 |
| 법령, 신고 절차, 정보공개서 문맥 | 버전된 Vertex AI RAG corpus | manifest 이후 개정 징후가 있거나 평가일 유효판이 corpus에 없을 때 | 최신 공식 원문을 먼저 저장·버전화한 뒤 재검색 |
| 본사 모집·후보지 출점 가능성 | 프로젝트 문서와 본사 회신 | 사용자 요청으로 특정 브랜드·후보지를 확인할 때 | 서면 근거가 없으면 `UNKNOWN` |
| 최신 매물·권리금 | 승인된 제휴 feed 또는 사용자 문서 | 사용자가 특정 매물을 검토하고 약관상 실시간 조회가 허용될 때 | 조회 결과를 실제 계약조건으로 확정하지 않음 |
| 지도 POI 보조 확인 | DS-005·006의 저장된 점포 관측 | 명시적 장소 확인 또는 저장 관측의 폐업 여부 점검 | 공급자 약관상 저장 가능한 필드만 보존 |
| source health | manifest와 마지막 성공 수집 | 장애·쿼터·스키마 변경 확인 | 데이터 Claim과 connector 장애를 분리 |

실시간 검색은 정상 결과 생성의 필수 경로가 아니다. 검색 장애 때문에 전체 워크플로를 실패시키지 않고 저장된 최신 승인 snapshot을 사용하되, 신선도 SLA를 넘겼으면 `STALE` 또는 `UNKNOWN`을 표시한다. 반대로 live 결과를 기존 snapshot보다 최신이라는 이유만으로 즉시 권위 Evidence로 승격하지 않는다. 원문 저장, 스키마 검사, 날짜·지역·단위 검증, 중복 검사를 통과해야 한다.

## 5. 첫 번째 프로덕션 데이터 팩

첫 팩은 **전국 P0 공개 근거 팩 `kr-cafe-grounding-p0-2026-08-23`**으로 고정한다. 민간 카드매출, 실제 매물, 권리금, 미래 성공률은 넣지 않는다.

정확한 구성은 다음과 같다.

1. `area-registry`: DS-001 법정동 현행·폐지 코드, DS-003 최신 제공 경계, 각 원천의 기준연도와 코드 매핑.
2. `population-monthly`: DS-004 최신 공표 월의 총인구·성별·연령대, 외국인 제외 플래그.
3. `cafe-observations`: DS-005 최신 전체 스냅숏의 카페 업종 매핑과 DS-006 휴게음식점 전체 스냅숏·최근 변경분. 업종 분류 버전과 인허가 상태 포함.
4. `franchise-finance`: DS-013 브랜드·가맹본부 identity와 DS-014 최신 신고연도별 창업금액. 현재 자동 계산에는 가맹금·교육비·가맹사업자 보증금·기타 초기금액과 공표 합계만 포함하며, 법적 정보공개서 등록번호·등록일·본문과 평균매출·점포 수·개폐점은 별도 후속 데이터 경로로 남긴다.
5. `rent-benchmark`: DS-010 최신 공표 분기의 상업용부동산 임대동향 표본 상권 값. “개별 매물 아님” 플래그 포함.
6. `cost-and-procedure`: DS-015~021의 평가일 현재 유효 요율·법령·표준서식. 시행일, 관할, 원문 조문 위치 포함.
7. `manifest.json`: 각 파일의 source id, 실제 URL, 요청 매개변수, HTTP 상태, 수집시각, 데이터 기준일, 라이선스 표기, SHA-256, 파서 버전, 행 수, 품질검사 결과.
8. `quality-report.json`: 코드 미매칭률, 좌표 결측률, 중복 후보율, 날짜 역전 수, 프랜차이즈 필수 필드 결측률, 경계 밖 좌표 수.

배포 승인 조건은 원본 해시 재현, 모든 원천 링크의 HTTP 성공 또는 공식 API 성공, 행 수 급변 경고 검토, 샘플 100건 원문 대조, EvidenceRecord 스키마 검증 통과다. 팩의 정확한 원천 데이터 기준일은 수집 실행 때 manifest에 기록해야 하며, 이 조사일을 데이터 기준일로 대신 쓰면 안 된다.

## 6. 결과 카드의 빈 상태를 없애는 구현 순서 1~6

1. **RAG hit를 EvidenceRecord 후보로 변환:** `retrieve_official_documents`의 hit마다 원문 id, anchor, excerpt, 원문 기준일과 `source_trace`를 반환하고, Control API의 `EVIDENCE_RETRIEVAL` adapter가 현재 Claim type·지리 범위·기준일을 결합해 후보 record를 만든다. Agent에는 이 후보를 전달하고, Evidence Freeze는 Agent가 수용한 id만 확정한다. 검색 hit 자체를 사실로 자동 승격하지 않는다. `source_trace`와 연결되지 않는 hit는 후보에서 제외하고 결과를 `PARTIAL`로 남긴다.
2. **전국 지역·카페 관측 연결:** DS-001~006을 `get_area_profile`, `search_cafe_observations`, `search_business_events`에 연결한다. 첫 화면에는 지역, 카페 수, 최근 개·폐업, 데이터 기준일을 제공한다.
3. **프랜차이즈 구조화 연결:** `list_franchise_universe`는 회사 공식 모집 근거로 개인 가맹 후보를 제한하고, `get_franchise_disclosure`는 그 후보의 DS-013 브랜드 identity와 DS-014 신고연도 창업금액만 보강한다. 법적 정보공개서 등록 여부·본문과 특정 주소 출점 승인은 이 데이터로 추론하지 않는다. 현재 창업금액 경로는 코드 구현·계약 등록까지 완료됐고 실제 snapshot 적재·배포 전이다.
4. **독립카페 손익분기 모델:** DS-010과 DS-015~018을 비용 기준선으로 연결하고, 매출 예측 대신 객단가·영업일·고정비 가정에 따른 손익분기 주문 수를 계산한다.
5. **공식 절차 RAG 채우기:** DS-019~021을 관할·시행일 메타데이터와 함께 공식 corpus에 적재하고 `get_official_procedure`를 프로덕션에 등록한다.
6. **프로젝트 문서 경로 열기:** DS-028~032 업로드, 가림, OCR, 사용자 확인, 공식 교차검증을 구현한다. 이후 계약된 DS-023·024·027만 선택적으로 추가한다.

각 단계는 MCP manifest, 프로덕션 능력 목록, Evidence planner Claim 매핑, health check, fixture가 아닌 실제 원천 read-back을 함께 갱신해야 한다. 도구 구현만 하고 능력 목록에 등록하지 않으면 현재와 같은 빈 결과가 반복된다.

## 7. 권장 신규 MCP connector

현재 목표 도구 이름과 맞출 수 있는 것은 계약을 재사용하고, 부동산·비용·민간 수요처럼 기존 계약에 없는 도구는 런타임 프로토콜의 주 버전 변경과 스키마 검토 후 추가한다.

| 도구 | 핵심 request | 핵심 response | 원천 | 실패 시 |
|---|---|---|---|---|
| `get_area_profile` | `administrative_code`, `boundary_version`, `as_of` | 지역 identity, 경계 ref, 인구 facts, source dates | DS-001~004 | 시점 경계가 없으면 boundary·집계 모두 UNKNOWN |
| `search_cafe_observations` | 지역코드, 경계 버전, 기준일, metrics | 카페 수, 인구, 서울 한정 수요 facts, coverage | DS-004·005·008·009 | 지원하지 않는 지역 지표는 누락 Claim으로 반환 |
| `search_business_events` | 지역코드, `CAFE`, 날짜 범위, `OPEN`·`CLOSE` | 인허가 사건, 상태, 관측일, source refs | DS-006·007 | 0건과 수집 실패를 별도 상태로 반환 |
| `list_franchise_universe` | `industry=CAFE`, `as_of` | 내부 브랜드 id, 표시명, 회사 공식 개인 가맹 확인 근거와 기존 비용 profile | 회사 공식 자료 + DS-013 identity 보조 | 모집 근거 없음과 조회 실패를 분리 |
| `get_franchise_disclosure` | 브랜드 id, 선택적 source version, 기준일 | DS-013 exact 브랜드·본부 identity, DS-014 신고연도 창업금액 구성항목과 공식 합계 | DS-013·014 | 불완전 구성항목은 finance override 금지; 법적 정보공개서 미확인은 별도 missing context |
| `get_official_procedure` | 관할, 절차 유형, 기준일 | 유효 조문, 단계, 제출물, 원문 위치 | DS-019~021 | 관할 규정 미확인은 전국 절차로 대체하지 않음 |
| `retrieve_project_documents` | 프로젝트 id, 질의, 문서 개정 id, limit | 가림된 구절, 표 셀, 원문 anchor, 사용자 확인 상태 | DS-028~032 | OCR 신뢰도 미달은 확인 요청 |
| `get_property_reference` | 지역, 점포 주소, 면적, 층, 기준일 | 집계 임대 참고, 건축물 용도, 실거래 참고, coverage | DS-010~012 | 실제 임대조건처럼 표시하지 않음 |
| `get_cost_reference` | 영업 예정일, 직원 구성, 계약전력, 매출 가정 | 최저임금·보험·전기·수수료 facts와 산식 입력 | DS-015~018 | 적용 조건 미상은 범위 또는 UNKNOWN |

모든 response는 자료값만 반환하지 말고 최소한 `source_ref`, `published_or_data_date`, `source_observed_at`, `geographic_scope`, `coverage_status`, `freshness_status`, `missing_context`, `durable_evidence_refs`를 포함해야 한다. 숫자 계산은 connector나 SQL에서 결정적으로 수행하고 모델이 원문 표를 읽어 합산하게 하지 않는다.

## 8. 공식 RAG corpus 구성

### 넣어야 할 문서

- DS-013·014의 정보공개서 원문과 항목 정의. 구조화 수치는 API·SQL에서 가져오고 RAG는 계약 조건과 문맥 설명에만 쓴다.
- DS-019의 식품위생법령, 시설기준 별표, 건강진단 규칙, 지정 교육기관 안내.
- DS-020의 사업자등록 공식 안내, 평가일 현재 유효 법령, 관할 자치법규.
- DS-021의 상가건물 임대차보호법, 최신 표준 임대차계약서, 표준 권리금계약서.
- DS-015~018의 유효 요율 고시·공식 안내. 계산용 정형 요율표는 SQL에도 별도 적재한다.
- 각 문서에 관할, 시행일, 개정일, 폐지 여부, 공식 원문 URL, 페이지·조문 anchor, 콘텐츠 해시를 붙인다.

### 넣지 말아야 할 데이터

- DS-004~012 같은 대량 수치·좌표·시계열. 이는 API·공간 DB·SQL로 질의한다.
- 네이버·카카오·Google 장소 응답 원문과 지도 타일. 장기 저장권이 확인되지 않았다.
- 사용자 계약서, 견적서, 대출 조건, POS, 등기 문서. 공식 corpus가 아니라 프로젝트별 격리 corpus에만 넣는다.
- 주민등록번호, 계좌번호, 서명, 전화번호, 전자우편, 정확한 개인 위치.
- API 키, 접근 토큰, webhook, 계약상 비밀 데이터.
- 오래된 법령을 최신 절차로 검색되게 하는 무버전 문서. 과거판은 별도 보관하되 유효기간 필터를 강제한다.

## 10. 조사 중 발견한 반례와 불가능한 약속

1. **API 응답이 실시간이어도 값이 최신이라는 뜻은 아니다.** 공정위 API의 조회시각과 정보공개서 신고연도, 주민인구 API 응답시각과 월말 기준일을 구분해야 한다.
2. **점포 행 수는 실제 영업 카페 수와 같지 않다.** 업종 분류 변경, 중복, 폐업 반영 지연, 복합업종 때문에 DS-005와 DS-006을 함께 써야 한다.
3. **과거 평균매출은 신규점 매출 전망이 아니다.** 공정위 평균매출을 후보지 예상매출로 표현하거나 본사가 해당 지역을 승인할 것이라고 약속할 수 없다.
4. **서울 상권 데이터로 전국을 채울 수 없다.** 서울 외 지역의 유동인구·추정매출·소비는 지역별 커넥터나 상업 계약이 없으면 UNKNOWN이다.
5. **임대료 표본 통계는 현재 매물이 아니다.** 보증금·관리비·권리금·특약은 사용자 문서나 허가된 매물 feed가 필요하다.
6. **전국 권리금 정본은 없다.** 권리금은 개별 협상과 계약에 달려 있으므로 자동 수집한 확정값을 약속할 수 없다.
7. **브랜드가 공정위에 등록되어 있어도 지금 신규 가맹을 받는다는 뜻은 아니다.** 후보지별 출점 가능성과 보호영역은 본사 서면 확인 전 UNKNOWN이다.
8. **지도 검색 API는 자유로운 데이터 warehouse가 아니다.** 특히 네이버 약관은 지역정보 별도 DB 구축을 제한하며, Google도 캐시와 지도 결합 제약이 있다.
9. **국세청 상태 API는 사업자를 발견하는 검색 API가 아니다.** 이미 적법하게 확보한 사업자등록번호만 검증할 수 있다.
10. **생존율은 성공 확률이 아니다.** 과거 집단 폐업·생존 통계로 특정 신규 점포의 성공을 보장할 수 없다.
11. **전국 단일 창업 체크리스트는 최종 답이 아니다.** 건축물 용도, 층·면적에 따른 소방, 옥외광고물, 관할 조례를 점포별로 확인해야 한다.
12. **정확한 세금·보험·공과금을 하나의 고정률로 약속할 수 없다.** 과세 유형, 매출, 인원, 계약전력, 적용연도와 감면 조건이 필요하다.

## 12. 품질 판정과 가장 큰 blocker

이 조사에 대한 신뢰도는 다음과 같다.

- 공공 데이터원의 존재와 책임 기관: 높음.
- 즉시 연결 가능한 API의 정확한 운영 쿼터: 중간. 공공데이터포털 개발 한도는 확인했지만 운영 승인 후 한도는 계정·API별로 달라질 수 있다.
- 민간 카드·매물 feed의 가격, 재배포권, 세부 필드: 낮음, `BLOCKED_BY_DATA`.
- 전국 지역별 가맹 가능성과 보호영역: 낮음, 본사별 서면 확인 전 `BLOCKED_BY_DATA`.

가장 큰 데이터 blocker는 **후보지별 최신 프랜차이즈 가맹 가능성과 실제 점포 계약조건을 전국 단위로 자동 확인할 공통 원천이 없다는 점**이다. 공정위 데이터는 비교의 출발점이지만 현재 모집 여부, 후보지역 승인, 보호영역, 실제 로열티·필수품목 협상 조건을 확정하지 않는다. 따라서 첫 제품은 공개서 기반 후보를 조건부로 제시한 뒤, 본사 회신과 사용자 계약 문서를 받아 확정하는 흐름이어야 한다.

그 다음 blocker는 서울 밖의 세밀한 유동·매출·소비와 전국 최신 매물·권리금이다. 이 값들을 확보하기 전에는 빈칸을 임의 추정치로 채우지 말고, 공개 전국 P0 사실과 손익분기 시나리오로 결과 카드를 구성해야 한다.
